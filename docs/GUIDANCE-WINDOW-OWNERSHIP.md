## Source-confirmed gap

At the original checkpoint, preparation restored an application PID (`OpenCompanionApp` and `CompanionShell.prepareScreenGuidance`). Capture used an exact selected window ID and owner, but `desktopIndependentWindow` could supply that window's pixels even when a sibling from the same PID covered it. Overlay and continuation ownership compared the foreground PID. Those checks did not establish that the selected window/control was exposed.

A selected window may also be followed by a region crop. Therefore `ScreenEvidence.screenRect` is not universally the complete captured window frame. A new geometry check must retain trusted whole-window capture bounds separately rather than infer movement from crop-size inequality.

The locally inspected public AppKit SDK documents `NSWindow.windowNumber(at:belowWindowWithWindowNumber:)` as a mouse-down destination query at a global logical point. Passing zero excludes no window. A nonzero exclusion skips that window and every window above it; using that as an assistant-panel workaround could also skip a real blocker. CoreGraphics documents its on-screen window list as ordered front to back.

## Implementation implications

Before cursor flight, annotation or action publication, a selected-window target needs exact current window-ID/owner/bounds checks plus a target-interior input-destination sample. The cursor's flight destination may lie outside the control, so it is unsuitable as the check point. Ordered higher-window bounds can conservatively refuse visual overlaps, including same-PID siblings. Only exact, currently tracked passive assistant panels may be exempted; interactive assistant windows must remain blockers. Bounding-box overlap is conservative and does not prove per-pixel occlusion.

Click observation needs a separate lease-bound mouse-down-to-mouse-up contract. The coordinator at that checkpoint saw mouse-up only. A menu can open on mouse-down, so a new hit query on mouse-up or after the settling delay can reject a legitimate transition and cannot authenticate the earlier destination. The public event PID and window-under-pointer fields are available, but their actual global-monitor delivery still needed native receipts. Unknown or contradictory ownership must not silently become PID-only authority. Every continuation still requests fresh perception and verifies progress; no observed click proves success.

Remaining native acceptance at that checkpoint included the actual passive cursor/annotation panels, selected A behind same-PID B, partial coverage, interactive own controls, move/resize/minimize/close, sheets, mixed scales/negative origins and legitimate menu transitions. The new guard and authenticated event handoff were **not implemented or verified by that experiment**. Complete external-task acceptance, latency targets and all **21 whole-product parity gates remained open**.

## Source implementation and verification checkpoint

The subsequent source implementation retains `ScreenEvidence.capturedWindowBounds` before any region crop and includes it in `ScreenEvidenceIdentity`. `screenRect` remains the actual captured extent. This preserves both the whole-window geometry needed to detect a moved/resized window and the narrower coordinate scope used by the model.

Before cursor flight, annotation or action publication, `AppModel` runs `GuidanceSelectedWindowCheck` for window-backed evidence. Its self-contained `GuidanceWindowVisibility` policy requires the exact selected ID/owner, unchanged whole captured bounds, positive on-screen visibility, target containment within the selected extent and a target-center hit matching the selected window. It validates raw finite bounded geometry, unique IDs and at most 4,096 records. Higher on-screen windows with positive alpha and bounds overlapping the target refuse admission, including same-PID siblings. This is a conservative metadata check, not per-pixel occlusion or compositor proof.

Passive exclusions are restricted to exact currently registered cursor and annotation window IDs. The host also checks their live `ignoresMouseEvents`, nonkey/nonmain capability and state; the pure policy independently requires the excluded window's owner to be this process. Interactive controls, explanation surfaces and arbitrary windows from the same owner are not excluded. The native hit query always uses exclusion value zero, so it does not skip an unknown real blocker along with an assistant panel.

Selected-window click continuation now observes both left-down and left-up. One pending down is bound to the current lease, frame, generation, request, step, target and deadline. Admission and current selection ownership remain required. The recorded down must be inside the target and carry a positive matching target PID plus exact public field 92, the window that can handle the event. Field 91 is not a fallback. Missing or contradictory down ownership refuses the pair. Matching up consumes it once while retaining foreground/selection/generation/deadline and target-point checks. It deliberately does not require the up's window to match: a menu can open on down. A known foreign up PID refuses; cancellation and rearm clear pending state. This observes interaction and requests fresh same-scope perception; it does not prove control activation or task success.
